# Concrete 52-bit local A64 mappings and ten full-width digits

This revision chooses an AArch64 implementation with FEAT_LVA and FEAT_LPA, using 64 KiB translation granules, 52-bit local virtual/physical addresses and level-1 4 TiB block descriptors. The protected model prices scalar 64-bit A64 instructions and explicitly permits analytic bounds; it imposes no 47-bit address ceiling. These are ordinary documented optional features, not arbitrary-width pointer arithmetic. An implementation without these features does NOT satisfy this construction. No claim is made that the review VM supports them or physically holds the exponentially large distributed attack.

Primary documentation: Linux's Arm64 memory-layout documentation describes 52-bit addresses with 64 KiB pages/three translation levels and the [51:42] first-level index: https://docs.kernel.org/6.12/arch/arm64/memory.html . Arm documents FEAT_LVA/LPA and the 4 TiB level-1 block for the 64 KiB granule with 52-bit PA: https://documentation-service.arm.com/static/6762ba2527eda361ad4e0432 and https://support.arm.com/documentation/ddi0602/2020-12/Shared-Pseudocode/AArch64-Translation?lang=en . Only these few architecture facts come from those references; the exact layouts, protocol, instruction counts and cold/memory bounds below are this submission's construction.

## Actual page tables and bootstrap work

Use a64KiB L1 table with1024 relevant first-level entries. Each4TiB-aligned contiguous LUT or child-aperture extent uses ordinary level-1 block descriptors. The256TiB child aperture uses64 such entries. Worker vectors/fixed LUTs total165 entries; no per-entry page table or page fault is needed during digit lookups. At the low address region, use an L2 table with512MiB blocks and an L3 table for64KiB pages containing code, constants, stack, source/reply/controller buffers and the small initialized private state. A separate L2/L3 pair maps the one parent64KiB page at4T or32T. At most oneL1+twoL2+twoL3=5*64KiB=320KiB suffice for these layouts. Count/pending/cache arrays can use their aligned surrounding block extents; any inaccessible guards or private low exceptions use the existing low-region tables. No data array is falsely included in the4MiB private code/state budget.

Reserve at most1MiB of that4MiB for all translation tables/configuration, leaving3MiB for code/stack/controller/source/reply/queues and arithmetic scratch; actual code and the64-message shard queue plus source buffers are well below this. Build and zero ALL descriptor tables, install TTBR/TCR/MAIR and local feature configuration, complete the required barrier/TLB initialization, then establish monitor wait state. There are NO runtime mmap/page-fault handlers, allocation scans, per-record TLB shootdowns or software-emulated address extensions. Large constants are actually built with MOVZ/MOVK during setup and retained in ordinary context/registers; hot public calls use their already charged argument moves/loads.

Coherent neighbor-page setup is the same explicit model as in the notification construction. The chosen real-blocking WFE/address-tagged-monitor implementation must ALSO have these ordinary large-address features. Timer/event streams, periodic interrupts, debug events and WFE traps remain disabled. Page mappings and configuration are stable before parking; no extra mapping changes clear monitors during the hot phase. A WFE-asNOP implementation or a machine without LVA/LPA does not support this bound. This is a disclosed implementation restriction, not a free scheduler/monitor or a physical qualification of the VM.
