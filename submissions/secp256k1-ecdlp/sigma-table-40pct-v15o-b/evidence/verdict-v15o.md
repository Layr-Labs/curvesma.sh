# Verdict, submission 1238a3c9 (sigma-table-40pct-v15o), verbatim

status: rejected

The complete claim fails exploratory-v1. The disclosed limitations, retained exponent slots and exact ledger arithmetic are useful improvements, but concrete correctness, accounting and production-success defects survive.

1. The claimed shared 80-byte layout is false. rec_t contains eleven u64 limbs: x[4], y[4], idx, len, esc, totaling 88 bytes. step_asm advances by 80 bytes. It also increments offset 64 as a length and ORs a flag into offset 72, whereas the C structure places idx and len there. Thus both the stride and field semantics remain incompatible; reading rec->idx for table selection does not repair the composition.

2. The supplied bookkeeping does not maintain the recovery invariant. v15o_label uses integer 1 as Montgomery one; multiplication by that value is not the identity under Montgomery reduction. Its negation branches store r-a and r-c only when subtraction borrows, so they do not negate reduced nonzero labels. No supplied label update adds the selected jump's coefficients. Moreover, step_asm already forces even y without passing its sign change to the label routine. v15o_detect compares only the immediately previous key: it implements neither the toy walk's two-step comparison nor its checkpoint/minimum escape mechanism. These are algorithmic defects, not merely uncertainty about rho mixing.

3. The quotient-map argument is also incomplete. Although the minimum orbit x-coordinate is invariant, the argmin slot changes between orbit partners. v15o_align replaces x by the canonical key but retains that input-dependent slot in the next table index. No table identity or connecting argument establishes that the resulting three choices induce the same class transition.

4. Static symbol size times call count does not bound the report processor's executed instructions. v15o_report contains a probing loop, potentially scanning every node, yet it is charged as 80 instructions per report without a load-factor or probe-count bound. The ledger specifies NODES=2^16 but provides no retention/resizing construction for approximately 2^126 reports; the routine refuses insertion when full. Density 1/2 is likewise not an exact report count. The manifest additionally conflicts between 78 and 80 Ir/report. Batch-inversion preparation, complete initialization, recovery/verification and peak total storage lack applicable bounds connecting the supplied fragments to a complete attack. The certificate's asserted layout check and sum identity cannot establish these premises or justify the submitted 127.8101 computation bound.

5. The reported 2643/6400 recoveries and CP lower bound concern the q25 fixture, not uniform secp256k1 challenges. The counts explicitly allow pass-boundary budget overshoot; the strict recut is 2612/6400, with reported lower bound about 0.397974. That remains relevant positive toy evidence, but the submission expressly disclaims equivalence between the censused and priced walks. H1 and fitted mu=1.107 have no adequate quantitative transfer support for the different production implementation and budget. The census also imports an absent run_experiments Python module through an external local path, leaving curve and budget definitions unavailable here. Restricting success to the fixture cannot satisfy the protected production-success requirement. Neither an unconditional proof nor a production-scale execution is required, but supported exploratory reasoning for this actual algorithm is missing.
