# Deterministic truncated baby-step/giant-step with sorted-array intersection on BLS12-381 G1

Parent submission package: `submissions/bls12-381-g1-ecdlp-plain` at
`6423c2728dc03d5f2d647c7f22adf1dac0643a66` (unscored template). This package
replaces it as the selected submission.

## 1. Instance

- `r = 0x73eda753299d7d483339d80809a1d80553bda402fffe5bfeffffffff00000001`
  (255 bits, `log2 r = 254.857089...`), `p = 0x1a0111ea...aaab`.
- `G1` is `y^2 = x^3 + 4` over `Fp`, generated by the fixed profile point `P0`,
  of prime order `r`. Only `G1` points of order dividing `r` are involved, so
  the cofactor never appears.
- Challenge: `x` uniform in `[0, r)`, input `T = [x]P0` (the identity when
  `x = 0`). Output `x`. Nothing else is supplied: no powers, no SRS, no `n`.

## 2. Algorithm

Exact integer parameters, chosen once from the public order `r`:

```
m = 143003466105892742053438571826631282054
h = 143003466105892742053438571826631282053
m*h = 20449991318299214286984618798192526676775745980111041990993247566413071176862
ceil(39*r/100) = 20449991318299214286984618798192526676699315475205778750815426892976046661961
```

so `m*h >= ceil(39r/100)` and `m*h < r`. The parameters are the balanced split
of `ceil(39r/100)`: `m = ceil(sqrt(target))`, `h = ceil(target/m)`, which
minimises `m + h` for the required product.

Steps:

1. If `T` is the identity, output `0` and stop (one comparison).
2. Baby chain: `B_0 = O`, `B_j = B_{j-1} + P0` for `j = 1..m-1`, giving
   `B_j = [j]P0`. Store the record `(x(B_j), j)` for every `j >= 1`; `B_0` has
   no affine coordinate and is excluded, which is why step 1 handles `x = 0`.
3. Sort the baby records by affine x-coordinate, treating the 381-bit
   coefficient as a six-word unsigned integer and comparing lexicographically
   from the most significant word.
4. Compute `S = [m]P0` once (double-and-add, 127 doublings and at most 127
   additions). Giant chain: `G_0 = T`, `G_i = G_{i-1} - S` for `i = 1..h-1`,
   giving `G_i = T - [i*m]P0`. Store `(x(G_i), i)` for every non-identity
   `G_i`; collect the indices with `G_i = O` separately.
5. Sort the giant records the same way.
6. Merge-intersect the two sorted arrays on the x-coordinate. Equal runs on
   both sides are expanded pairwise, so no duplicate key is skipped.
7. For every match `(i, j)` — meaning `x(G_i) = x(B_j)`, hence
   `G_i = B_j` or `G_i = -B_j` — form the two candidate scalars
   `c1 = (i*m + j) mod r` and `c2 = (i*m - j) mod r` and accept the first with
   `[c]P0 = T`.
8. For every collected identity giant index `i`, test the single candidate
   `i*m` directly (it is already reduced because `i*m < m*h < r`).
9. If nothing verifies, report failure.

### Why the sign branch is needed and why it is cheap

The affine x-coordinate determines a point only up to sign, so a sorted
intersection on x finds `G_i = B_j` (giving `x = i*m + j`) and also
`G_i = -B_j` (giving `x = i*m - j`). Both candidates are tested by an exact
scalar multiplication, so neither branch can return a wrong scalar. For a
fixed `x` the congruence `x = i*m + j` has exactly one solution with
`0 <= j < m`, and `x = i*m - j` has at most one more; therefore at most two
candidates are ever tested. A spurious x-coordinate collision between
unrelated points is impossible: two G1 points share an x-coordinate exactly
when they are equal or opposite.

## 3. Success probability — exact, no heuristic

The map `(i, j) -> i*m + j` is injective on `[0, h) x [0, m)`, so the
recoverable scalars are exactly

```
S = { i*m + j : 0 <= i < h, 0 <= j < m } = [0, m*h) ∩ Z,
```

and `S` is contained in `[0, r)` because `m*h < r`. Step 1 covers `x = 0`
(also in `S`, at `i = j = 0`), and steps 6–8 cover every other element of `S`.
For uniform `x` in `[0, r)`:

```
P(success) = |S| / r = m*h / r
           = 20449991318299214286984618798192526676775745980111041990993247566413071176862
             / 52435875175126190479447740508185965837690552500527637822603658699938581184513
           >= 39/100.
```

There is no hashing, no probe sequence, no eviction, no drop rule and no
random table layout. The table contains every baby record that exists and the
merge inspects every giant record, so the success set is the rectangle above
for every single run. The only random object in the probability space is the
challenge `x`; the algorithm itself consumes no coins.

## 4. Cost ledger

Notation from `tracks/docs/COST_MODEL.md`: `C = 2000` scalar AArch64
instructions per BLS12-381 G1 reference operation (batched incomplete affine
addition, 6M with `S = M`, `A = 0`). Total work is `W = H + R/C`, where `H` is
the number of reference operations and `R` the remaining instruction count.

### H — reference operations

| Item | Count |
| --- | ---: |
| baby chain `B_1..B_{m-1}` | `m - 1` |
| `[m]P0` by double-and-add | `<= 254` |
| giant chain `G_1..G_{h-1}` | `h - 1` |
| candidate verification, at most 2 scalars, each 255 doublings + `<= 128` additions | `<= 766`, charged `800` |
| identity-giant tests (integer only) | `0` |

```
H = m + h + 1056 = 286006932211785484106877143653262565163.
```

### R — scalar instructions

Sorting is charged as a radix sort of 64-byte records (48-byte x-coordinate
plus 16-byte index). Twelve passes of 32-bit digits cover the six words of the
x-coordinate; the index words ride along as payload.

Per record and per pass, the counted instructions are: load the digit word
(1), load/add/store the bucket counter (3), load the scatter index (1),
compute the destination address (2), store the eight record words (8), store
the incremented counter (1), loop control (4) — 20 instructions. Twelve passes
give 240 instructions per record.

| Item | Instructions |
| --- | ---: |
| baby sort | `240 m` |
| giant sort | `240 h` |
| merge-intersect, 20 per element (12 loads, 6 compares, 2 branches) | `20 (m + h)` |
| radix bucket prefix sums and clears, 12 passes x `2^32` buckets x 2 | charged `2^36` |
| identity tests, parameter arithmetic, output encoding, state | `1024` |

```
R = 260*(m + h) + 2^36 + 1024 = 74361802375064225867788057349916986145580.
```

The merge performs the lookup; there is no separate search structure, so no
lookup cost is omitted or double-counted. Memory transfers are counted through
the load/store instructions above; the model counts instructions, not cycles,
so cache behaviour adds nothing further.

### W

```
W = H + R/2000
  = 32318783339931759704077117232822105823579 / 100
  = 3.2318783339931759704077117232822105823579e38
log2 W = 127.92564049370783 <= 127.925641.
```

Submitted score: `127925641/1000000`.

### Parallelism

Every item above is charged once, on one processor. The sort could be split
across processors, but the model sums work across processors, so splitting
changes nothing in `W`; no coordination cost is assumed away.

## 5. Memory

One record is 64 bytes: a 381-bit coefficient stored as six 64-bit words
(48 bytes) and a step index below `2^128` (16 bytes).

```
peak = 64*(m + h + max(m, h))   baby + giant + radix scratch
     + 2^35                     bucket counters, 2^32 x 8 bytes
     + 2^20                     code, parameters, state
     = 27456665492331406474260205790747566941248 bytes
log2 peak = 134.334280...  <= 134.335.
```

Memory is supplementary under `classical-group-work-v2` and creates no
objective or tie-break; it is stated because the rules require it. The
exponential table is inherent to a square-root-time generic attack at these
parameters, and it is not hidden: the claim is analytic and no production-size
run is asserted.

## 6. Preprocessing and advice

Preprocessing is the target-independent part: the baby chain and the baby
sort.

```
preprocessing = m + 240 m / 2000 = 1.12 m
              = 4004097050964996777496280011145675897512 / 25
              <= 2^126.913.
```

It is included in `W` (the `m` term of `H` and the `240 m` term of `R`). The
giant chain depends on `T`, so it is attack work, not preprocessing.

Nonuniform advice is `0` bytes: nothing is stored between runs, no
parameter-dependent table is embedded in code, and the baby table is built
from the public generator at run time and charged in full. The claim is a
single cold attack on one target and is not amortised over future targets.

## 7. What is deliberately not assumed

- No random-oracle, uniform-hashing, cuckoo, or probe-window model. Those
  models are what make a hashed table's success probability depend on the hash
  draw; this package avoids them entirely by sorting.
- No "expected number of dropped records" term. Every baby record is present
  in the sorted array and every giant record is compared, so the success set
  is exactly `[0, m*h) ∩ Z`.
- No heuristic about the distribution of the baby x-coordinates. The sort and
  the merge are correct for arbitrary keys; their cost does not depend on the
  data beyond the fixed radix pass count.
- No free advice, no uncharged verification, no uncharged sorting or memory
  movement.

## 8. Objections considered

- *Is the success probability really exact?* Yes. The recovered set is a
  rectangle in `Z/r`, its size is `m*h`, and `x` is uniform. The identity
  challenge and the identity giants are handled explicitly, and the sign
  ambiguity is resolved by verification rather than assumed away.
- *Could the merge miss a solution?* A solution satisfies `x(G_i) = x(B_j)`,
  so the two records have equal sort keys and the run-expansion in step 6
  yields the pair. Distinct points can share an x-coordinate only when they
  are equal or opposite, which is exactly the case the two candidates cover.
- *Is the sort cost realistic?* The radix sort is charged at 20 instructions
  per record per pass over 12 passes. A comparison sort would cost about
  `127 * 20` instructions per record, roughly ten times more; the radix figure
  is the conservative choice actually used, and the per-instruction breakdown
  is listed above.
- *Is the truncation legitimate?* The rules require success at least `0.39`
  and charge all trials; truncating the giant chain to `h` steps is exactly
  the trade that produces `m*h/r = 0.39...`, and the loss is stated as the
  exact failure probability `1 - m*h/r`, not as a heuristic.
- *Does anything depend on `n`?* No. This track has no `n` parameter and no
  auxiliary powers; the parameters depend only on the public order `r`.
