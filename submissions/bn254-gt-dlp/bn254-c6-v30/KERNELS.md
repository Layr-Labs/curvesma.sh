# KERNELS.md: Scalar ARMv8.1-A Integer Kernels with Disclosed FEAT_LSE STADDH and LDADD

All inner loops use scalar general-purpose-register ARMv8.1-A integer instructions (-march=armv8.1-a -mgeneral-regs-only, simd = 0; no NEON/SVE, DC ZVA, fp64, TABM or external C/Callgrind measurements; the instruction counts of the kernels listed in kernels_v30.s are read and checked by audit_bn_cm.py, and kernels_v30.s assembles with clang -arch arm64 -march=armv8.1-a with 0 errors), plus two disclosed scalar FEAT_LSE atomic integer instructions from the same ARMv8.1-A LSE family, each priced at 1 scalar instruction = 1 / 20,000 units under COST_MODEL.md:
1. `STADDH Ws, [Xn]` (32-bit alias of `LDADDH Ws, WZR, [Xn]`; scalar registers; base-register `[Xn]` addressing only), used for score updates on C[s].
2. `LDADD Xs, Xt, [Xn]` (64-bit scalar atomic fetch-and-add; base-register `[Xn]` addressing only), used on E_0 inside Lattice Band 2's 9-op direct-to-link-page emit (`ldadd x1, x9, [x8]` with `x1 = #8`) to fetch and post-increment `ptrs[s]` in one instruction (executed instruction by instruction in `v25_verify.py lat_apply_e2e`).

Every score cell satisfies `init_a[ai] + sum_{p | N_g} floor(16*log2(p)) <= 32,768 + 16*529.15 = 41,234 < 65,536` (also on the SWAR coordinate box), so uint16_t accumulation never wraps in a logical cell `1 <= ai <= N_a(b)` (guard and trap cells and the dummy sink collect unrelated writes and may wrap; they are never used as scores), and STADDH is bit-identical to `ldrh; add; strh` (`staddh_16b_semantic_errs = 0` on 4,096 inputs).
