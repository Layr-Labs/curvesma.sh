## 1. Exact kernel body charge with explicit fixed-call row

The declared dependency 49e06a3d proves a 1025-instruction worst-path side-output body and charges 1026 per side output, using the extra instruction per output and padded operation to fund fixed invocation costs. This package charges the 1025 body exactly and funds fixed calls through a separate, nonoverlapping ledger row instead.

The side call is issued at most once per round per base, so (BASES+2)*LANE_OPS bounds the invocations (the dependency's call bound, retained). Each invocation costs at most 512 instructions including call preparation and return (deliberately larger than the 36 fixed function instructions reported by the native audit). The ledger therefore adds an exact row of 512*(BASES+2)*LANE_OPS = 1066509928891664157045105880989696 instructions, split evenly between preprocessing (baby phase) and online work; the even split is asserted exact. This row is in the instruction total; fixed-call funding draws on no per-output slack, no allowance capacity, and no padding conservatism.

The body bound, restated from the declared dependency 49e06a3d. Let p be the base-field prime and R=2^384>8p. For a,b<2p, word-serial Montgomery reduction returns S=(ab+qp)/R with q<R, hence S<4p^2/R+p<2p, and the word accumulator stays below a+p<3p<R; so the first product (a=y1+y2<2p, b=inv<p) skips its final conditional subtraction, yielding mu<2p, while the square keeps its normalization and stays canonical. The second product takes both operands below 2p with raw output S<2p. For the final y, D=S-y1 lies in (-p,2p); one carry branch then adds p once (negative case, modulo-R arithmetic giving the unique value in [0,p)) or conditionally subtracts p once (nonnegative case), replacing 13+23 instructions by at most 23. lazy_witness.py derives side_lazy.S from measure/side_lanes.S by exactly this transformation (asserted byte equality), and native_check.py audits the resulting instruction stream against whole-integer field arithmetic (458 lanes, both branches). The stored y, parity key, and all downstream values are identical to the source kernel.

A pair costs 2000+1025+53=3078 instructions for two points; a root costs 2050. The primary 2000 reference charge is retained untouched, including its batch-inversion amortization, which a side-output formula alone does not replace. Pair bookkeeping (53) and root bookkeeping (50), including their seven-instruction worst-path parity keys, and the average record transport 81/2 are unchanged. With the unchanged pair fraction F=49/50, the weighted per-point charge is 39743/25 = 1589.72 instructions.

## 3. Explicit pool-cap charge and allowance 5

The source charges an 8-instructions-per-point allowance row for bookkeeping the listings may have missed, and names its largest known residual: the owner pool-cap compare, two instructions per baby record (source-proof.md section 5.2). This package charges that residual explicitly instead of carrying it inside the allowance: every baby record is inserted once into its owner's pool, and the insert path performs one pool-counter bound compare plus its not-taken branch (subs/cmp plus b.hi, two instructions), so the ledger adds an exact row of N*2 = 128479157619630390520503450019967396 instructions. Giant records only read their head slot and walk the chain (REC_LOOK); they never insert and need no pool-cap check. The pool-cap row sits entirely in the baby phase and is included in preprocessing in full.

With the pool-cap residual and the head-index combine made explicit, the allowance row drops from 8 to 5 instructions per point (2N*5 = 642395788098151952602517250099836980). Net of the two new explicit rows, the change removes 2N instructions (1 per point on average) while making the dominant residuals auditable rather than assumed: 8 to 5 saves 6N, the pool-cap row costs 2N, the head-index row costs 2N.

Aggregate residual bounds. Predecessor attempts at this allowance level were rejected first for comparing the retained margin only with the largest single residual, then for two specific accounting gaps; this revision bounds the aggregate for every named class and answers both gaps (verdicts cited as procedural context only). (i) Pool-cap compares: charged exactly (N x 2 above), residual zero. (ii) Primary-key reloads: zero. The side kernel stores the key to the record slot and the generator reloads it with the listed ldp+ldr pair (side records; loop control for main records); the key then travels inside the 40-byte record through already-charged loads, and no listing reloads a key anywhere else. (iii) Head-index word combine: charged exactly by a new row. The specified 57-bit index (key bits 60..116) straddles two 64-bit words on the stated record layout, so one extraction instruction cannot produce it; the least sequence is lsr plus bfi (two instructions where the listing charges one). The index is consumed by the head load on the next instruction, so no re-extraction path exists and the residual beyond the new row is zero. (v) Plan, batch and output pass control: below 2^115.2 instructions, over 13x below the retained margin. Owner-init loops dominate the remainder: per owner 2^56 charged stps iterate with subs+b.ne control, unrolled fourfold at identical stp count (setup inside the listed +64 per owner), giving below 2^115.01 including the outer owner loop; even without unrolling, below 2^117.1. ## 6. Segment-index encoding repair (33 bits)

The source specifies a 32-bit segment index in the record chain id (source-proof.md section 4.2) while allowing classes with up to 2^33 segments (section 3 under the H2 length bounds), so the index overflows on long classes. This package amends the encoding explicitly (verdict cited as procedural context only): the segment-index field is 33 bits in both the pool record (62-bit base index + 33-bit segment index + 56-bit link = 226 of 256 bits, within the 31 spare bits) and the 128-bit transport chain id (62-bit base index + 33-bit segment index + spare = 95 of 128 bits). The segment directory already holds 2^33+1 eight-byte entries and needs no change, and the 62-bit base index needs no change (at most 2^61.6 bases). The repair costs zero instructions: stores write the same words, loads read the same words, and the candidate re-walk's index extract widens an immediate only (ubfx width 32 to 33, still one instruction); record sizes, memory, and all occupancy and cap analysis are unchanged.
