Work is the sum of instructions executed over all processors (COST_MODEL.md: "Charge total work across processors, including preprocessing, advice construction, random sampling, all trials and failures, sorting, lookup, memory transfers, verification, output and success amplification"; rules.md: "Sum work across processors; do not amortize"). ## 1. Problem and reduction

Given T = [s]P0 and A_i = [s^i]P0 for i = 1..n, n >= 2^20, recover s. Let d = 2^20. Since v_2(r-1) = 32, d | r-1 and 6d | r-1. H = {x^d : x in F_r^*} has order m = (r-1)/d, log2 m = 234.857089. z = s^d is uniform in H and A_d = [z]P0 is an input. Only T, A_1 and A_d are read, so the same W applies to every n >= 2^20.

Lemma 1 (recovery of s from z). Twenty successive square roots in F_r (Tonelli-Shanks, each a few hundred F_r multiplications) give one t with t^d = z. Then s = t * zeta for one of the 2^20 d-th roots of unity zeta = g^k, g a fixed primitive 2^20-th root. Write k = i + 2^10 j: compute the 2^10 points [t g^i]P0 and the 2^10 points [g^(-2^10 j)]A_1 (2^11 scalar multiplications, 2^23 units), sort the first list by x and look each point of the second up in it. Charged at 2^24 units in the ledger.

Lemma 2 (mu6 in H). The group mu6 = {+-1, +-omega, +-omega^2} of sixth roots of unity lies in H because 6d | r-1 (asserted by the script). On this j = 0 curve [omega](x, y) = (beta x, y) and [-1](x, y) = (x, -y), so the six points [u]X, u in mu6, share the unordered pair {y, p-y}.

## 2. Algorithm A

H-primes. A prime q is an H-prime if q^m = 1 mod r. The walk list W is the set of H-primes w_0 < w_1 < ... above 2^39, taken in order until L of them are listed (L < 2^51.6504) (last element about 2^77.4, and at most 2^78 by H2). Base H-primes a are the first 2^65 H-primes above 2^80, the first 2^64 for the baby side and the next 2^64 for the giant side; the search that finds them H-tests at most the first 2^86 primes above 2^80, all of which lie in (2^80, 2^80 + 2^92] (H2, Section 6). Every scalar x = a w is below 2^93 x 2^78 = 2^171 < r, so x is a well-defined element of H and (a, w) is recovered from x by unique factorisation.

Chains. Chain a holds X_j = [a w_j]Q, with Q = P0 on the baby side and Q = A_d on the giant side. X_{j+1} = X_j + [a g_j]Q where g_j = w_{j+1} - w_j is even and, by H2', at most 2^33 except for at most 16 gaps of at most 2^34, each split into two table steps (Section 3); the table G_a[g/2] = [a g]Q has 2^32 affine entries (96 bytes each, 2^38.6 bytes) and is built by repeated addition of [2a]Q in 2^16 strands. Each strand starts with one scalar multiplication; strand 0 starts at k = 2 (entry k = 1, the point [2a]Q itself, is the one extra scalar multiplication in the ledger), so the first addition of every strand is [2ka]Q + [2a]Q with k >= 2. The chain itself runs as 2^16 lockstep segments of at most ceil(L / 2^16) < 2^35.6504 steps (segment starts by scalar multiplication), so each round is 2^16 independent incomplete affine additions sharing one Montgomery inversion. Each addition is the reference operation (batched 6M); the round's one F_p inversion is not part of the 6M convention and is charged separately (Section 4).

Lemma 3 (no degenerate addition). X_j = +-[a g_j]Q would need w_j = +-g_j in H, impossible since w_j > 2^39 > g_j > 0 and w_j is prime. So no doubling or point at infinity occurs in the chains or the table strands (table strands add [2a]Q to [2ka]Q with 2 <= k < 2^32: equality would need k = +-1 mod r, false). The toy builds its small tables by scalar multiplication, so it exercises the chain half of this lemma only; it asserts a non-zero denominator at every batched step.

Key. The record for X = (x, y) is (key, id): key = bits 1..192 of the even one of y and p - y (192 bits), id = 64-bit chain index. 32 bytes. By Lemma 2 the six points [u]X have the same key.

Lemma 4 (distinct ratios). Baby point [a w]P0 equals [u][a' w']A_d = [u a' w' z]P0 for some u in mu6 iff z = a w / (u a' w') in F_r. Such a pair has equal keys by Lemma 2, but the converse does not hold: the key keeps only 192 bits of y, so a truncated-key match does not imply the same orbit. It is a candidate, which the charged false-match handling (Section 3) and the scalar verification [z]P0 = A_d (Section 2) resolve. As fractions of integers, the N^2 ratios a w / (a' w') are pairwise distinct except on the diagonal w = w' (fraction 1/L of pairs, below 2^-51.65), by unique factorisation with a, a' in disjoint sets. Their images in H, and the six mu6 multiples of each, can coincide; Lemma 4 only rules out the trivial repeats. That the 6 N^2 (1 - 1/L) candidates cover z like independent uniform elements of H, to within the 0.0005 allowance stated in Section 6, is heuristic H1, and the success line rests on it (support: an exact census of the candidate set on toy primes, Section 6).

Order of the sides. The whole baby side runs first: every baby record is generated, routed and inserted before any giant chain starts, and a giant record is only ever compared against a complete table. The 2^20 generating nodes each run one chain at a time (2^44 baby chains each, then 2^44 giant chains each), holding one gap table at a time, which is the generating-node figure of at most 2^39.1715 B.

Routing. 2^84 owner nodes, node index = key bits 0..83, read as three 28-bit fields (t, u, v). Each generating node scatters records into 2^28 send blocks of 16 records (512 B) by t; a full block is posted to the hop-1 relay for t, which is owner node (t, 0, 0). That node re-scatters the records it receives by u into its own 2^28 send blocks and posts full blocks to the hop-2 relay for (t, u), owner node (t, u, 1), which re-scatters by v and posts to the owner (t, u, v). Every node has one send array of 2^28 blocks and three receive FIFOs, one per hop, and the relay work is executed at the relay and charged per record (listing in Section 4). Three hops, each a data-independent copy of 32 bytes plus addressing, posting and polling. Within an owner node, baby records are inserted into a direct-mapped head array of 2^33 8-byte slots indexed by key bits 84..116, chained through a pool of 2^33 32-byte records (capacity above 2.54 x the mean, which is below 2^31.651). The node index and the head slot are implied by where a record sits, so a pool record stores key bits 117..191 (75 bits), the 64-bit chain id and a 33-bit link to the next pool record, the rest spare; a head slot is a 33-bit pointer to the first pool record and a 7-bit count. A head slot holds at most 64 baby records; a 65th makes the node report fail. Giant records are not stored: a giant record reads its head slot and compares its 75 remaining key bits with each pooled record on the chain (8 instructions per comparison: load 24 bytes, compare, branch, pointer advance, and a decrement of the node's comparison counter). Equal key gives a candidate record (key, id, id'): the full 192-bit key, reassembled from the node index, the slot and the stored bits, and both chain ids, 40 bytes, appended to the node's candidate list of 2^16 slots. A 2^16 + 1st candidate makes the node report fail.

Per-pair verification. After the giant side, every owner node reports its candidate count through the status tree below; if the total exceeds 2^44 the run outputs fail. Otherwise each 40-byte candidate is copied into one 512-byte block for each of the two generating nodes g(id) and g(id'), where g(id) is the top 20 bits of the chain id, posted and polled (charged 128 instructions per candidate). Each generating node has a candidate receive area of 2^24 slots x 40 B; a 2^24 + 1st candidate makes it report fail. Then each of the two chains is re-walked once, linearly, from its start to its end by the generating node that owns it (its gap table rebuilt, its strands and segments restarted, all charged as in the table), and at every step the key of the point is extracted and compared with the retained key: the 47 instructions of walk overhead from the baby listing plus 32 (parity select and key extraction 23, compare 8, position bookkeeping 1), 2079 per step with the addition. The positions whose key equals the retained key are kept, at most 4 per chain; a fifth makes the run output fail. g(id') sends its kept values a' w' to g(id) as one 168-byte block (40 B header plus 4 x 32 B; copy, post and poll charged at 256 instructions). g(id) now holds at most 4 values a w and at most 4 values a' w', so at most 16 pairs, and for each pair the six z = a w / (u a' w') are tested by [z]P0 = A_d: at most 96 scalar multiplications per candidate, all at g(id). On a hit g(id) runs Lemma 1 and writes s into its status record. Nothing is ever compared against the whole other chain, so the re-walk is O(L) per chain, never L^2. A wrong candidate never produces a wrong answer. Charged in full for every candidate up to the cap (Section 3).

Node overflow and caps, all enforced locally. An owner node fails if it receives more than 2^33 baby records, if any head slot exceeds 64 records, if its candidate list exceeds 2^16, or if its comparison counter, preset to cap_node = ceil(1.01 x the node mean), below 2^30.316, reaches zero; a generating node fails if its candidate receive area exceeds 2^24; a node that fails stops and the run outputs fail. The global candidate cap is 2^44 (checked from the per-node counts before any re-walk), and a re-walk fails if one chain carries the retained key at more than 4 steps. The work charged is the maximum: every record, 2^84 x cap_node comparisons, every candidate up to the cap with the full 96-multiplication recovery.

Status collection. Every node keeps a 48-byte status record: s if found (32 B), then a fail flag (1 bit), its candidate count (17 bits; a node fails above 2^16) and its own baby and giant counts (34 bits each, at most 2^33 before a node fails), 86 bits in the remaining 16 B. Each node checks its own baby and giant caps, so the counts are not summed up the tree: a combined record holds the OR of the fail flags, the sum of the candidate counts saturated at 2^45 (46 bits; only the comparison with the 2^44 global cap uses it) and one found s, if any. It is collected three times, after the baby side, after the giant side and after recovery, through a fan-in-256 tree over all 2^84 + 2^20 + 2^30 nodes (depth 11): a node posts its record, or the combined record of its 256 children, to its parent. Charged at 2^12 instructions per node per pass in the ledger.

## 3. Sizes, caps and success

N = L 2^64 with L the least integer such that 6 N^2 >= 0.51 m: L < 2^51.6504, N < 2^115.6504, K = 6 N^2 / m, at least 0.51 and below 0.51 + 2^-51.7. Under H1 the probability that z is among the 6 N^2 (1 - 1/L) off-diagonal candidates is at least 1 - exp(-K) - 0.0005; 1 - exp(-K) rounded down is 0.399504 (Section 6).

Comparisons. 2^117 head slots in total, load lambda = N / 2^117, below 0.393 per slot. The giant side makes sum over slots of (baby count x giant count) comparisons, mean N^2 / 2^117, below 2^114.301, per node below 2^30.301 against the node cap, 1.01 x the node mean rounded up (below 2^30.316). Three per-node tails under H3, each already multiplied by the number of nodes or slots: (i) a head slot with more than 64 baby records, Poisson(lambda) tail at 65, 2^-273 over all 2^117 slots; (ii) a node's baby or giant count more than 2^-10 (0.098 %) off its mean, Chernoff, 2^-1460 over all nodes (both counts within 2^-10 puts the conditional mean at most (1 + 2^-10)^2 - 1 < 0.196 % above the nominal, and 0.196 % + 0.8 % < 1 %); (iii) given (i) and (ii), the node's comparisons are a sum of its giant records' independent slot draws, each a baby count in [0, 64] with second moment lambda + lambda^2 (the ledger takes 4 x this), so Bernstein with M = 64 and deviation 0.8 % of the mean gives 2^-10552 over all nodes. Every tail in this document is rounded towards the larger probability. The 1 % cap is therefore essentially never reached and the charge 2^84 x cap_node is a bound on the total.

False matches. Pairs with equal 192-bit key but different mu6 orbit: mean N^2 / 2^192, below 2^39.301, cap 2^44, Chebyshev tail below 2^-47.5 under H3. True matches: I budget 2^20 of them inside the same cap. Off the diagonal (w != w') their number is Poisson under H1 with mean at most K (below 0.51 + 2^-51.7), and it exceeds the budget with probability below 2^-20477385. On the diagonal it is not Poisson. If z = a / (u a') for one baby base a, one giant base a' and one u in mu6, then at every walk position w the baby point [a w]P0 and the giant point [a' w]A_d = [u^-1 a w]P0 lie in one mu6 orbit, so this one event gives L > 2^51.65 true matches, more than the budget and more than the 2^44 cap (L > 2^44 is asserted by the script). In that event the run outputs fail: the candidate counts that the status tree collects after the giant side total at least L > 2^44, unless a node has already failed on one of its own caps, and that check comes before any candidate is forwarded or re-walked. These z form a set of at most 6 n_b^2 = 6 x 2^128 elements of H, with n_b = 2^64 base primes per side, and z is uniform in H, so the event has probability at most 6 x 2^128 / m, below 2^-104.27; it is a separate failure term in the success line below. Outside that event, per node the candidate count is Poisson with mean (N^2 / 2^192 + 2^20) / 2^84, below 2^-44.699, so the chance that any of the 2^84 nodes exceeds its 2^16 candidate slots is below 2^-2929329. Per generating node the forwarded candidates have mean 2 (N^2 / 2^192 + 2^20) / 2^20, below 2^20.301, against a 2^24-slot receive area; the chance that any of the 2^20 generating nodes exceeds it is below 2^-39722907.

Re-walk key repeats. Under H3 a chain of L steps carries some key twice with probability about L^2 / 2^193, below 2^-89.6, and carries one key at more than 4 steps with probability below L^5 / (5! 2^768); over all 2^65 chains that is below 2^-451. Both are far inside the 2^-40 budget below. The step with the retained key is found by the linear re-walk because the key is a function of the point and the chain is deterministic from its start.

Node overflow. Mean below 2^31.651 baby records per node, capacity 2^33 (above 2.54 x). Under the binomial form of H3 the Chernoff bound per node is 2^-(3.2 x 10^9); times 2^84 nodes it is still astronomically small. I budget 2^-20 for modelling error.

Gaps. The walk list lies in (2^39, 2^78] (H2), where the mean gap between H-primes is at most 2^20 ln 2^78 = 2^25.76, so the expected number of gaps above 2^33 among its L - 1 gaps is below 2^-166.9 (exponential gaps, H2'); a larger gap is split into two table steps and the ledger reserves 2^69 units for 16 such splits per chain; a separate row charges what the reserve's reference price leaves out, the 47-instruction walk overhead of each reserved split addition and the 2 x 16 split steps of each re-walked candidate pair at cap, at their maximum although this path has expected count below 2^-166.9. The list construction checks the gaps and stops the run with no scalar if more than 16 exceed 2^33 or one exceeds 2^34. A split delays one segment by one round; Section 4 counts those rounds.

Success claimed, under H1 to H3: 0.399504 - 0.0005 - 2^-20 - 2^-40 - 2^-104.27 > 0.399 (the script prints 0.399503 after the three failure terms and 0.399003 after the H1 allowance as well, both rounded down). The 2^-40 covers every cap and re-walk tail above (each is below 2^-47); the 2^-20 is the modelling budget for node overflow; the 2^-104.27 is the diagonal true-match event; the 0.0005 is the coverage allowance of H1 (Section 6).

## 4. Instruction listing per record (AArch64 scalar, on top of the 2000-instruction reference addition)

Baby record (listed 147): gap stream read and pointer advance 5; gap stream transport from the storage nodes (4 bytes per step, blocked) 3; table address 2; operand loads and stores for the addition beyond the reference's own 18; batch-inversion prefix and suffix product loads and stores 6; lane control and loop 8; flow control and counters 5; the F_p inversion shared by the round, amortised over the chain's records (below) 4; parity select and key extraction 23; scatter at 3 hops (block index, slot, bounds, 12 per hop) 36; post and poll of full blocks amortised over 16 records at 3 hops 9; transport copy of 32 bytes at 3 hops (4 ldp/stp pairs plus addressing, 6 per hop) 18; insert (head load, slot count check, link write, record store, head update) 10.

Giant record (listed 143): the same without insert, plus lookup fixed cost 6 (head load, chain pointer test, end). Comparisons are charged separately at 8 each up to the node cap. The hop items are executed at the generating node, the two relays and the owner; all are charged per record wherever they run. The first seven items (gap stream through flow control, 47 instructions) are the walk overhead, and the same 47 are charged on every gap-table addition and every re-walk step; the inversions of the gap tables and the re-walks have their own ledger rows.

Charged: 180 per record on both sides, 33 above the listed baby count (1.22 x), as a margin for items I did not list.

Field inversions. Every F_p inversion is the Fermat power y^(p-2) by binary exponentiation: p - 2 has 381 bits, 229 of them set, so 380 squarings and 228 multiplications, 608 in all, each charged at the 383 instructions the cost model measures for one blst_fp_mul (S = M): 232864 instructions per inversion. The 6M reference convention covers the batch products of Montgomery's trick but not this inversion. F_p inversions occur in four places. (i) Record generation: each round of a chain's 2^16 lockstep segments shares one inversion. A chain runs at most ceil(L / 2^16) rounds, plus at most one more for each of the at most 16 split gaps (Section 3), so its inversions cost 232864 x (ceil(L / 2^16) + 16) / L < 3.56 instructions per record, listed above as 4. (ii) Gap tables: each round of a table's 2^16 strands shares one inversion; a strand makes at most 2^16 additions, so a table needs at most 2^16 rounds, 2^65 x 2^16 inversions over all tables (ledger row). (iii) Re-walks: a re-walked chain runs the rounds of (i) and its rebuilt table the rounds of (ii), so a candidate pair costs at most 2 (ceil(L / 2^16) + 16 + 2^16) inversions, charged for every candidate up to the 2^44 cap (ledger row). (iv) Scalar multiplications: each ends with one inversion, inside its 2^12-unit price. The six z of a kept pair are formed in F_r: one Fermat inversion y^(r-2) per kept giant value (254 squarings and 163 multiplications, 417), at most 4 per candidate, the 8 integer products a w and a' w', and per pair one multiplication for a w / (a' w') and six for the z (one by each element of mu6, which is closed under inversion, so no u is inverted), at most 16 pairs: at most 1788 multiplications per candidate, each charged at 383 instructions (ledger row). No other step inverts: Lemma 1 computes g^(-2^10 j) as g^(2^20 - 2^10 j), and the square roots and H-tests use only multiplications.

## 6. Heuristics

H1 (coverage). The 6 N^2 (1 - 1/L) distinct rationals a w / (u a' w') hit z nearly like independent uniform elements of H. Precisely: let R be the set of the mu6 multiples in H of the off-diagonal ratios a w / (a' w'), w != w'. The lists do not depend on the challenge and z = s^d is uniform in H, so the probability that z is an off-diagonal candidate is exactly |R| / m; a z among the diagonal values a / (u a') is the separate failure term of Section 3. Independent uniform elements in the number of these ratios would cover at least 1 - exp(-K (1 - 2^-51.65)) of H in expectation, which differs from 1 - exp(-K) by less than 2^-52. The census below has primes under that value (13 of 32 at m in [2^30, 2^31), lowest -0.00024), so H1 is not stated as that bound. H1 is the statement that at production size |R| / m >= 1 - exp(-K) - 0.0005, a coverage within the census deviation: every census prime from m = 2^26 up lies inside it, the primes at 2^24 and below do not all, and the spread across primes falls about as m^-1/2 (Trend, Margin). The success line carries the 0.0005 as an explicit term (Section 3); a shortfall up to 0.0095 would still leave the success above the required 0.39 (both asserted by the script). Lemma 4 removes only the trivial repeats (equal fractions), so H1 stays a heuristic. Its support is an exact count of R on toy primes, below.

Census (mode `census`). For a toy prime r = 6 c 2^k + 1 with m = (r - 1) / 2^k, H the subgroup of index 2^k, the script builds the lists by the production rules: an H-prime is a prime q with q^m = 1 mod r; the walk list is the first L H-primes above w_min = w_max^(39/77.4) (production: 2^39 and about 2^77.4); the base primes are the first 2 n_b H-primes above 2^2.6 w_max (production: 2^80 over 2^77.4), the first n_b baby and the next n_b giant; n_b is within 10 % of N^(64/115.6503), the production split, and L is the least integer with K = 6 n_b^2 L (L - 1) / m >= 0.51, so K counts only the off-diagonal pairs, as production's K (1 - 1/L) does. H2 / H2' (H-prime availability and gaps), stated over the exact windows that the two capped searches examine. Support: the density heuristic that a fraction 1/2^20 of the primes in each window are H-primes, which the expected counts below use exactly; prime counts use the bounds of Rosser and Schoenfeld, pi(x) > x / ln x for x >= 17 and pi(x) < 1.25506 x / ln x for x > 1. Walk list: the search sieves the integers in (2^39, 2^78] and H-tests its primes in increasing order, stopping at the L-th H-prime. The window holds between 2^72.24 and 2^72.58 primes, all inside the 2^73 H-tests charged. H2 states that at least L (below 2^51.6504) of them are H-primes; the expected count is above 2^52.24, at least 1.50 times L. Base primes: the search sieves the 2^92 integers in (2^80, 2^80 + 2^92] and H-tests their primes in increasing order, at most 2^86 of them as charged, stopping at the 2^65-th H-prime. The window holds more than 2^86.005 primes, so the search examines at most the first 2^86 primes above 2^80, never a prime beyond the sieved window. H2 states that at least 2^65 of those first 2^86 primes are H-primes; the expected count is 2^66, twice the need. Gaps (H2'): among the L listed walk H-primes at most 16 consecutive gaps exceed 2^33 and none exceeds 2^34; with exponential gaps of mean 2^20 ln q <= 2^25.76 in the window, the expected number above 2^33 is below 2^-166.9. If a search finds too few H-primes, or the walk list breaks the gap bound, the run stops before any chain starts and outputs no scalar; the lists do not depend on the challenge, and the success line is stated under H2 and H2', which exclude that case. Sanity on this r: 402 of the 6542 primes below 2^16 are 16th powers (expected 408.875) and 27 are 256th powers (expected 25.55).

H3 (key bits). The 192-bit keys of the 2N records behave like independent uniform strings across mu6 orbits: node and slot occupancies are binomial and cross-orbit key equality has probability 2^-192. Support: the toy bins truncated keys into 32 pseudo-nodes x 16 heads and the chi-square statistic matches its expectation (31.32 against 31, standard error 0.42). That agreement is consistent with the H3 occupancy model at toy size; it does not certify the production independence and concentration that every cap and tail bound in Section 3 uses, and those rest on H3 as a stated premise.

## 7. Evidence (`evidence.py`, standard library; the declared run took 3.3 to 3.5 s on the author's machine, longer under heavy load)

`ledger`: every number above from exact integers, the assertions d | r-1, 6d | r-1, mu6 in H, L > 2^44 (the diagonal event overflows the candidate cap), the success inequality after every failure term, the node memory sums and the exact memory inequality, the per-slot, per-node, candidate, diagonal-event and re-walk tails and the H2 sanity count; the prime counts of the two H2 windows, with asserts that the 2^73 charged H-tests cover every prime of the walk window, that the base window holds more primes than the 2^86 H-tests charged, and that the expected H-prime counts exceed the needs (each floating-point one is at least 0.3 % from its threshold); the inversion counts from the bits of p - 2 and r - 2, with the integer assert that the listed 4 instructions per record pay every record round's inversion; the asserts that the success line tolerates a coverage shortfall of 0.0005 against the claimed 0.399 and 0.0095 against the required 0.39 (Section 6); the exact integer asserts W^200000 <= 2^23355819 and ceil(pre / 2000)^10000 <= 2^1157815 for the preprocessing quote.

`ec`: Algorithm A end to end on the j = 0 curve y^2 = x^3 + 3 over F_207670579 of prime order r = 207671809 (d = 128, m = 1622436): H-primes from a sieve, 15 chains x 25 steps per side (K = 0.5201), gap tables, batched affine walks asserting no zero denominator, 16-bit parity key binned into 32 pseudo-nodes x 16 heads, comparisons and false matches counted, each candidate kept as (key, id, id'), one linear re-walk of each of its two chains collecting the steps whose key equals the retained key (at least one asserted; more than 4 on either side counts the trial as a miss, reported as `rewalk_cap_fails`), the six z tested against A_d for every pair of kept steps, then 7 square roots and the root-of-unity scan. The toy never compares one chain against the other. It is not the production procedure at small size, and these are the differences: the comparison, slot, candidate, pool and 2^44 caps are not enforced, the counts are compared with the model instead; the re-walk cap is enforced and counted as a failure; all 15 chains of a side advance in lockstep instead of 2^16 segments of one chain; the re-walk uses the stored small table with complete affine additions and one inversion per step; Lemma 1 scans the 128 roots of unity linearly in batches of 16 instead of a sort and lookup; it is one process, so nothing is routed, posted or polled; candidates are processed in the order found, duplicates included. 400 trials, seed 2026 (the hosted input): success 0.4025 against 0.3935 predicted with the toy diagonal loss (z = +0.37); comparisons 276.2 per run against 274.7 expected; false matches 2.2 against 2.146; true matches 0.51 per run against K = 0.52; re-walk cap failures 0; every recovered s correct. 2000 trials, same seed, run locally (about 15 seconds): success 0.3895 against 0.3935 (z = -0.37, standard error 0.011); comparisons 275.4; false matches 2.104; chi-square 31.17 against 31 (standard error 0.18); re-walk cap failures 0; every recovered s correct. Both toy runs sit at K' = 0.5001, 0.0099 below the production K = 0.510000, and neither separates the claimed 0.399 from the required 0.39 (Section 6).

`census`: the exact count of R described in Section 6, on toy primes built by the production rules, at any toy size the input names (m_bits, k, K_percent, first_seed, primes, seconds; no further prime starts once `seconds` have passed, and the output says whether that happened). In the declared run (mode all) it counts 8 primes, k = 2, 4, 7 and 10 at seeds 0 and 1 with m in [2^21, 2^22), at K from 0.5105 to 0.5254, in about 0.7 s: mean diff +0.000577, lowest -0.000567, highest +0.002030, 3 of 8 below 1 - exp(-K), every prime through its 40 spot checks. At this size the spread across primes is 0.0012 to 0.0014 (the neighbouring sizes in Section 6), so these 8 primes show the method and the size of the deviation at small m; the larger sizes of Section 6 carry the trend.

## 8. Limitations and what was not done

Analytic bound, no full-size run. The instruction counts are itemised, not measured on hardware; the cluster model is the one stated in the cost accounting above, mine and not a rule of the challenge. H1 is supported by an exact census of the candidate set on toy primes up to m = 2^34.9 and H3 by the toy run; neither is proved at production size. Memory is exponential as in any BSGS-form Cheon attack. This package is 0a45ddb2's bucket-matching package (hprime-bucket-v1) with one parameter change, K = 0.51 instead of 0.52: N, L and every number derived from them are recomputed by evidence.py, and the caps, the cluster model and the toy procedure (mode ec, whose output now also prints its diagonal-corrected K') are unchanged; the listing gains one item, the shared inversion. Two statements inherited from 0a45ddb2 are corrected, without changing the algorithm or any ledger row. Its true-match tail ignored the diagonal event (z = a / (u a') gives L true matches from one base pair, so that budget is exceeded with probability at least 1/m, not below a Poisson tail); Section 3 now accounts the event as a separate failure term below 2^-104.27. Its Lemma 4 said that an equal key means an orbit match; a truncated-key match is only a candidate. Two gaps in the inherited accounting are also closed, again without changing the algorithm or the value of any inherited ledger row. H2 named the base range (2^80, 2^99), while the capped base-prime search examines at most the first 2^86 primes above 2^80; H2 is now stated over exactly the windows the two searches examine, with the expected counts and what the run does on a shortage (Section 6). The F_p inversion shared by each round of 2^16 additions was performed but neither listed nor charged by name; it is now listed per record (4 instructions, inside the 180 charged) and charged by new rows for the gap tables and the re-walks, with a row for the F_r inversions that form the six z (Sections 4 and 5). The three rows add about 2^88.7 units, and a fourth row (2^63.59 units) charges the walk overhead of the split additions that the 2^69 reserve prices at the reference addition, and the re-walks' split steps; the score is unchanged. The H1 margin is thinner than in 0a45ddb2 (0.399504 against the required 0.39, 0.0095); a new census mode counts the coverage exactly at K = 0.51 itself on toy primes (Section 6), and production success still rests on H1. Negative results from my own search, not claimed: two-for-one P+Q / P-Q (needs w +- g both H-prime), x-only or projective steps (no saving against the batched affine reference), rho inside H (loses the one-addition step), two routing hops (send blocks do not fit a node), records under 32 bytes (false-match cap breaks). The pinned llm-verifier was installed and run on this folder: preflight valid, intake snapshot built; the declared initial run was replayed in the runner's file layout (entrypoint plus files/, python -I -B, empty working directory, input on stdin), in 3.3 to 3.5 seconds on the author's machine (longer under heavy load). The hosted run of the revision before 0a45ddb2 completed inside the 20 second budget and reproduced the ledger; that revision was rejected on two points, both fixed in 0a45ddb2 and kept here: the candidate record did not retain the matched key and the toy compared the two re-walked chains against each other (now the key is retained and each chain is re-walked once, Section 2), and the memory bound counted every node at 2^40 B and reported 124.0 after rounding when the sum was above 2^124 (now the exact itemised sum, Section 5). A further fresh-context review of that fixed revision found thirteen gaps: the walk overhead was not charged on the gap tables and the re-walk, the kept values of the giant chain had no path to the node that uses them, the relay nodes and the pool record layout were not named, there was no status collection, the toy was described as the production procedure, some tails were rounded the wrong way, and wording. All are closed in 0a45ddb2 and here; the new rows and the raised gap-table and re-walk prices add about 2^92.4 units against a record term above 2^116.77, so the score fraction is unchanged. The script was also run directly under Python 3.10, 3.12 and 3.14 with identical output, and the intake gates (file limits, manifest keys, claim score spelling, experiment schema and budget) were replayed with a separate check written against the pinned verifier source.
