# bls12-381-g1-ecdlp: Cheon subgroup walk with fixed-base comb tables

Claim: for s uniform in Z_r^* and inputs T = [s]P0, A_i = [s^i]P0 (i = 1..n, n = 2^20),
the algorithm below recovers s with probability at least **0.40**, using at most
**2^120.890005** target-group-operation equivalents at n = 2^20 (score 24178001/200000),
including table construction, trail starts, distinguished-point storage and detection
delay, the square-root chain, verification and output. Peak memory is at most
2^33.383252 bytes. Preprocessing is 2^20 units, and nonuniform advice is 0 bytes.

This is a classical cold attack on one target. It is not a practical break, and nothing
beyond a generic walk with the auxiliary powers is claimed. The success bound rests on
the disclosed heuristic H1 (random-mapping behaviour of the walk) and on the toy
measurements in section 6. The per-step instruction count in H3 is a blst Callgrind
measurement with a margin (section 3).

Files: `accounting.py` recomputes every number here with exact integers (uses the
vendored `exact.py`; output in the table below). `experiment.py` is the bundled toy
experiment (stdlib only, generated by `tools/bundle.py` from `cscore.cheon`).
`evidence/` holds the toy runs and the blst step measurement (`evidence/measure-blst-step/`).
Input and output conventions follow `submission.json`.

## 1. Reduction

Let r be the group order, d = 2^20 (which divides r−1 since r−1 = 2^32·odd), and
H = {x^d : x in Z_r^*} the subgroup of d-th powers, |H| = N = (r−1)/d. Since
s is uniform in Z_r^*, h = s^d is uniform in H.

- A_d = [h]P0 with h in H. This is a discrete logarithm in H with base P0.
- Given h, the 2^20 candidates for s are the d-th roots of h. Recover s by twenty
  square roots, fixing each sign by the public power A_(2^j): with t_20 = h,
  for j = 19 down to 0 take a root t_j of t_(j+1) with [t_j]P0 = A_(2^j). The true
  s^(2^j) is one of the two roots, and the other fails the check. Finally s = t_0,
  checked against T = A_1.

So the cost is that of solving the subgroup DL [h]P0 = A_d in H, plus about 40 scalar
multiplications (about 10^3 units, negligible).

## 2. The walk on H modulo mu6

mu6 = {1, −1, λ, −λ, λ², −λ²}, where λ is a cube root of unity mod r. Since 6 | N,
mu6 lies in H. On G1, −1 is negation and λ acts as the endomorphism (x, y) → (βx, y).
Every point P has a class of size 6 under mu6. Let M = N/6 = 2^232.272 be the number of
classes, and write ~P for the canonical representative.

Canonical form: among the six images of P under mu6 pick the one whose x-coordinate is
least, with y reduced to its parity normalisation. This costs one multiplication by β
(x → βx, and βx' = −x−βx for the third image) and a comparison. Its exponent is the
tracked multiple of the base, so a canonical point is always [c]B for the exact integer c
the walk tracks.

Multipliers: 64 elements g_1..g_64 of H, drawn uniformly as x^d for random x. Their cost is
nil, since multiplication of exponents is done mod r without touching G1.

Step rule. For a canonical point with key k = x(canonical) and tracked exponent c:
- j = f(k) = (k >> 90) mod 64 selects the multiplier;
- c' = c·g_j mod r;
- the new point is [c']B evaluated by a fixed-base comb on the base B, then canonicalised,
  with the exponent updated by the canonicalising mu6 element, c ← μ·c'.

Two families share the same rule. Tame trails use B = P0 and start at random c_0 in H.
Wild trails use B = A_d, with the exponent relative to A_d. Both families apply the
same function f on classes, which is what makes tame–wild collisions useful.

Distinguished points: a canonical point is distinguished when its low 90 key bits are zero
(probability θ = 2^−90). A trail stores each distinguished point (key, family, exponent)
and continues. It is restarted after 2^100 steps (CAP), which is far below sqrt(M) and so
avoids cycles within a trail.

Collision. When a tame (exponent c_t) and a wild (exponent c_w) distinguished point share a
key, their canonical points are equal, so [c_t]P0 = [c_w]A_d = [c_w·h]P0. Hence
h = c_t·c_w^{−1} mod r exactly. Verify [h]P0 = A_d, then run the chain of section 1.
Tame–tame and wild–wild collisions are ignored, since they carry no information about h.

No fruitless cycles: with random multipliers, a 2-cycle needs g_j·g_k in mu6 for some pair,
which has probability at most 64²·6/N, negligible. The walk is a Teske r-adding walk on
the cyclic group H modulo mu6 with r = 64 pseudo-random step sizes, which is the setting of
section 3.

Why not additive steps: adding a fixed point R = [e]P0 moves the exponent off H, so the walk
would leave the subgroup and the cost falls back to plain rho on G1 (2^126.5). The
multiplicative steps and the canonical choice of multiplier are what keep the walk inside H.

## 3. Success probability

Let S be the total number of walk points (tame and wild) performed before a collision is
detected, and let M be the number of classes.

**H1 (random mapping, disclosed).** The class walk behaves like a random mapping on the M
classes. Under H1 the probability that the S points contain a tame–wild collision is
1 − exp(−S²/(4M)), since there are S/2 tame and S/2 wild points.

**H2 (walk bookkeeping).** Detection of a merged pair waits for both trails to reach the
next distinguished point, at most 1/θ = 2^90 expected steps per trail, so detection adds at
most 2K·2^90 steps in total, where K = S/(2·2^100) trails per family. This is included in
S_total. A trail that does not reach a distinguished point within CAP steps has probability
at most e^−1024, and a cycle inside one trail has probability at most (2^100)²/(2M) ≈ 2^−33,
over all trails about 2^−16. Both are negligible and the wasted steps are counted.

**H3 (per-step instruction count).** Each step performs 16 batched affine additions (the
comb), which are charged as reference units and not executed by the measured kernel, and
other scalar work: one β multiplication and the parity handling for canonicalisation, two
multiplications mod r (exponent update and mu6), digit extraction and table indexing, and the
distinguished-point test. That other work was measured on blst (the organizer's library) with
the organizer's Callgrind method: (1382037 − 689925) / 256 = 2703.56 instructions per step,
from runs of 512 and 256 steps (`evidence/measure-blst-step/`). The charge is 2800 per step:
that measurement plus about 100 for walk-loop and trail bookkeeping the kernel does not run.

**Model value.** Choose S so that 1 − exp(−S²/(4M)) = 1 − e^−0.6 = 0.4512, i.e.
S_coll = ceil(sqrt(4·M·3/5)) = 1.5492·sqrt(M). The claimed lower bound is 0.40, a margin of
0.05 below the model for H1 and finite-size effects. Section 6 shows the observed rate is
close to the model and above 0.40 pooled over 1210 toy trials (0.416, Wilson 95% about
[0.40, 0.43]).

## 4. Computation

Work is W = H + R/C with C = 2000 (G1 price, `tracks/docs/COST_MODEL.md`). H counts batched
incomplete affine additions (reference units). R counts other scalar instructions.

| Component | Count | H (units) | R (instructions) |
| --- | --- | ---: | ---: |
| walk steps | S_total ≈ 2^116.769 | 16·S_total | 2800·S_total |
| comb tables for P0 and A_d (2·16·2^15 points) | 2^20 additions | 2^20 | 0 |
| trail starts (2K comb evaluations) and chain (41 comb checks) | ~2^21 | 16·(2K+41) | 0 |
| square roots (20 Tonelli–Shanks), six candidate checks, inversion | bound | — | 2^20 + 2^16 |

With S_total = S_coll + 2K·2^90 and S_coll = ceil(sqrt(4·M·3/5)), the exact totals are:

| Quantity | Value |
| --- | --- |
| log2 S_coll | 116.767581 |
| log2 S_total | 116.768989 |
| H (log2) | 120.768989 |
| R/C (log2) | 117.254416 |
| **time_log2 = log2 W(2^20)** | **120.890005** (= 24178001/200000) |
| preprocessing (log2 units) | 20.000001 (both comb tables) |
| success model / claimed bound | 0.451188 / 0.40 |

**Range of n.** The bound uses A_1, A_(2^j) for j ≤ 20 and A_d = A_(2^20). It therefore holds
for every n with 2^20 ≤ n < r, with the same W, and the scored value is W(2^20). For
n < 2^20 nothing is claimed.

**Accounting convention.** Every walk step is charged in full, including the wasted
detection steps and the trail caps; sums are over all trails and processors, with no
amortisation over future targets. Table building (both bases) is charged, although the
P0 table depends only on public constants. The attacker's verification is one comb
evaluation.

## 5. Memory and advice

Peak storage: distinguished-point table at load factor 2, 2·S_total·2^−90 entries of 48
bytes, which is 2^33.35 bytes; the two comb tables, 2·16·2^15 affine points of 192 bytes
(201,326,592 bytes, 2^27.58); trail state 2K·64 bytes (about 2^22.8); code and scratch 16 MiB.
The total is 2^33.383252 bytes (about 10 GB). Nonuniform advice is 0 bytes, since the comb
tables are built from the challenge's public points at run time and charged above.

## 6. Evidence (toy scale)

The toy (`experiment.py`, from `cscore/cheon.py` in curvesmash-core) runs the full walk and
the chain on a generic prime-order group. Points are opaque labels (keyed hashes of the
exponent): the attacker sees equality, multiplication by known integers and the mu6
action, and never the exponent. The toy group has the mu6 action, so the walk and the
collision statistics are those of section 2. It is not a BLS12-381 curve, so it tests the
statistics and not the per-step cost.

| --- | --- | ---: | ---: | --- |
| toy-initial-b32-k6-60.json | 32, 6, 60 | 60/60 | 0 | 0.333 [0.227, 0.459] |
| toy-k6-400.json | 32, 6, 400 | 400/400 | 0 | 0.415 [0.368, 0.464] |
| toy-k8-400.json | 34, 8, 400 | 400/400 | 0 | 0.410 [0.363, 0.459] |

| toy-b38-k10-200.json | 38, 10, 200 | 200/200 | 0 | 0.445 [0.378, 0.514] |
| pooled, mult = 64 (1210 trials) | | 1210/1210 | 0 | 0.416 [about 0.40, 0.43] |
| toy-mult16-b32-k6-400.json (ablation, mult = 16) | 32, 6, 400 | 400/400 | 0 | 0.383 [0.336, 0.431] |

Every trial recovered s exactly and no collision gave a wrong h. The model overshoots the
pooled rate by about 0.035, which is why the claim is 0.40 and not 0.45. Ablation: 16
multipliers make the walk about 8% slower in steps, and 64 match the model well, so the
claim uses 64. The multiplier count changes no per-step cost in section 4.

The toy runs and the claimed cost are reproducible with the commands in section 8. The toy
is limited to bits ≤ 32 and k ≤ 8 by the schema, while the bits 36/38 runs are offline
evidence beyond the schema.

## 7. Limitations and heuristics

- **H1** is the random-mapping heuristic for the class walk. Its support is the toy data
  above, the Teske r-adding walk analysis (r = 64) and the random-mapping argument, not a
  proof. The margin of 0.05 covers the observed shortfall of about 0.035.
- **H3** rests on a blst Callgrind measurement of the non-addition work (2703.56 per step)
  with a 100-instruction allowance for bookkeeping. The kernel (`evidence/measure-blst-step/cheon_step.c`)
  reads a 64-entry table per window; its instruction count does not depend on table size, and
  table memory traffic is not charged, as for every other cache effect. The kernel's reference
  pass attributes the Fp multiplication to `ref_fp_mul.constprop.0`, which its toggle misses, so
  the reported split between reference and other work is off by that multiplication. The total,
  which the score uses, is unaffected.
- **Comb costs** count additions only; table loads are charged at zero beyond the
  additions, and cache effects are not charged (the score counts instructions).
- The walk does not need the powers A_i for 2^j ≠ d except in the square-root chain, whose
  cost is negligible.
- Memory is about 10 GB. Larger comb windows trade memory for steps: with window 20 the
  time is about 2^120.62 with 2.6 GB of tables, and with window 24 about 2^120.40 with 35 GB
  (`work-cheon/scripts/window_tradeoff.py` in the research folder). This candidate uses window 16.

## 8. Reproduction

```sh
python3 -I accounting.py
echo '{"bits":32,"k":6,"trials":60,"seed":2601}' | python3 -I experiment.py
```

`accounting.py` prints `time_log2` = 24178001/200000 (= 120.890005) and the memory bound. The
blst measurement is in `evidence/measure-blst-step/`: `cheon_step.c` is run by the organizer's
harness (`measure.sh cheon_step.c blst inputs.txt out` with `N1=256 N2=512` and
`REF_FUNCS="ref_fp_mul ref_fr_mul"`), and `python3 -I replica.py <target-profile.json> inputs.txt 512 dump-512.txt`
checks the container's dump. The inputs come from `python3 -I gen_inputs.py <target-profile.json> 7`. The file `inputs.txt` itself
(203,562 bytes, SHA-256 `96392535045d08f03434014273af3dbc17622a5d80ab1841ca52a12f591125a0`) is not
in the package because it exceeds the 64 KiB per-file limit; that command regenerates it byte for byte.
The toy unit tests live in curvesmash-core: `python3 -m unittest discover -s tests` from that
directory.
