## 1. Success: two arms, one binary

Arm A (dense, `dp_bits=0`) is the census instrument v10g already had; arm B is the **declared
production pipeline** (`dp_bits` 4/6/8) — DP-triggered sparse records, Montgomery batch inversion
over the 16 slots, pairwise match and solve on sparse records only.

`recproc.json` carries the listing counts (`mul_once` 140, `recproc` 40, `batch_inv` 982) and the
ladder structure (256 squarings + 128 multiplies = 384 `fe_mul`); `p256_recproc.c` is the source
that was compiled. The inversion is amortised over 2^16 walkers because that is the declared
production batch (`ledger.json:record_pipeline.batch_walkers`), whose state is 2^23 B.

## 3. Storage, in exact integers

| quantity | value | field |
| --- | --- | --- |
| record layout | 32 B x + 32 B packed (a,b) + 8 B tag = 104 B | `cap.json:record_bytes` |
| S | 2^127.632 steps | `cap.json:log2_total_steps_S` |
| sparse records | 2^65.632 | `cap.json:log2_sparse_records` |
| sparse bytes | 72 x 2^66 = 2^71.79 B | `cap.json:sparse_bytes_ceil` |
| cap | 2^73 B | `cap.json:declared_cap_bytes` |
| slack | 0.83 bits | `cap.json:slack_bits` |
| dense bytes at S | 2^133.79 B, 61.17 bits over cap | `cap.json:dense_over_cap_bits` |

The dense configuration is therefore impossible under the declared cap; that is the design
necessity for the sparse predicate (verdict item 3), not a performance choice.

## 4. Fixture

`(q+1)/2 = 549,756,820,252 = 2^39.000003` classes (`ledger.json:fixture.classes_log2`), not
2^40.000. Both fixture and production are pre-capture relative to their budgets; that premise is
declared, not proved, and §1's sparse rows are quoted as fixture measurements only.
